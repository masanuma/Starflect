## 固定した条件

- 架空人物：1990年5月15日生まれ。時刻不明。現在のアプリの仕様どおり12:00 JSTで近似し、上昇星座は省略。
- 対象：2026年9月9〜15日、各日08:00 JST。7日分の計算を先に確定してから生成。
- `astronomy-engine` を使う既存の `astro.ts` と `readFortune` を呼び出した。出生10天体と、現行の抽出規則で選ばれる上位四つの運行配置を保存。
- モデル：現行サーバーと同じ `claude-sonnet-5`。`max_tokens: 1500`、`thinking: adaptive`、`effort: low`。同じ依頼文「今日のわたしの運勢を教えて」を使用。
- 一日・一方式につき一回、計14回の初回生成。APIエラーなし。全件 `end_turn` で完了。出力を選び直す再生成はしていない。
- 合計入力29,789トークン／出力5,159トークン。価格の換算はしていない。
- 両版とも当該日の配置と「朝」を渡した。旧版の本番仕様に合わせ、対象の暦日自体は生成モデルへ渡していない。曜日に基づく予定や出来事も入力していない。
- 気分・会話履歴・人格要約はどちらにも追加しない。七日分の他日の文章も渡さない。
- 旧版の生年月日表記・人格導入に対し、新版は星の材料をJSON形式で渡し、編集指示に人格導入を含める。生の生年月日は新版に重複して渡していない。情報の見せ方と出力構造も変更しており、単一要因だけの実験ではない。

## 初回生成から分かったこと

**新方針を文章で指示するだけでは、まだ狙った体験まで届いていない。**

- 新版9月9日と10日は、両方とも火星への追い風を軸に「身軽に動く」話になった。配置が続く事実は正しいが、具体的な楽しみの描き分けは弱い。
- 新版12日と13日は、「動きたい／落ち着きたい」のせめぎ合いが中心。注意日の支えが、ペース配分の助言へ戻りやすい。
- 新版14日と15日は、「じっくり整える」満足が続いた。整った文章や見出しが増えても、日ごとの読後感は自動で変わらなかった。
- 新版は七本すべてに注意欄を付けた。「必要な日だけ」という指示を守るには、欄の有無を判断する工程も必要そう。
- 新版13日の「午前は静かに、午後は少し動く」は過ごし方の提案として読めるが、時刻別の計算に基づく予測ではない。9日の「午前のうちに気持ちが張り詰めやすい」、15日の「すれ違いやすい時間帯」も、この一時点の材料からは時間の特定を支えられない。編集案ではそうした時間の示唆を外した。
- 旧版にも具体的な助言や受け止めの良さがある。特に13日は対人の反応を自分の魅力の不足と結び付けない言葉がある。一方で、原因を星だけに帰す言い方は強いため、そのまま新方針の基準にはしない。

これらは今回の14本に対する編集上の所見であり、利用者の反応やモデル全体の性能を測った結果ではない。

## 編集案で変えたこと

1. 見どころを行動力などの概念から、共有・再発見・好み・遊びなどの日常で想像できる情景にした。
2. 同じ配置が続く9・10日は、同じ週の連続性を残しつつ、採用する主軸を変えた。日替わりの幸運イベントは捏造していない。
3. 13日は恋愛の衝突を予告する代わりに、相手の反応に左右されない好きの時間を提案した。難しい配置を大吉扱いにはしていない。
4. 11・13日は別枠の注意を省いた。毎回「でも気をつけて」で閉じない。
5. 相談の入口を、本文を読んで気になりそうなことに寄せた。ボタンとしての操作や、実際の相談回答はまだ作っていない。

編集案本文は190〜207字。星の根拠は各日の末尾に明示した。ただし、天体の位置は計算結果、日常の情景は占星術的な編集・解釈である。例えば特定の曲・写真・本の出来事を天体が予測したという意味ではない。

## 次の実装に持ち越す課題

今回、利用者に渡す文章の見本は作れたが、同等の文章を毎日自動で作れるとは未確認。方向が好みに合えば、まず新しい生成指示に「配置を選ぶ→日常の情景にする→重複・根拠を点検する」という編集過程を組み込み、初回出力と比較する。

さらに、過去数日と同じ文章になる問題、時間帯の根拠、相談の返答を確認する。前日の文章を参照する仕組みを足すかは、その段階で判断する。今回の編集案のためだけに作った七日分の演出を、そのまま毎日運用できると見積もらない。

## ファイルと再現

- `inputs.json`：出生黄経、七日分の計算結果、旧・新の完全なシステムプロンプト、現行ハンドラーのSHA-256。
- `raw-generations.json`：14本の未編集本文、モデル名、生成時刻、トークン使用量、プロンプトのハッシュ。認証情報は含まない。
- `new-editorial-prompt.md`：新方針の初回生成に使った指示。
- `edited-new.json`：Codexによる編集案と根拠。
- `scripts/prototype-week.ts`：準備・生成。サーバーコードをメモリ内で読み込み、現行のプロンプト関数を呼ぶ。本番エンドポイントは使わない。
- `scripts/render-prototype-week.mjs`：保存済み原稿からMarkdown資料を組み立てる。7日・14原稿・根拠参照を検査。

リポジトリのルートで実行する。

```powershell
# 資料を組み立て直すだけ。API呼び出しなし。
node scripts/render-prototype-week.mjs

# 現在のコードから入力を再計算する。inputs.jsonを上書きする。
node --import tsx scripts/prototype-week.ts

# 新規生成が必要な場合のみ。設定済みAPIを使う。
# 同じ日・版・プロンプトの保存結果は再利用する。
node --env-file=.env --import tsx scripts/prototype-week.ts --generate
```

厳密に今回と同じ入力を確認する場合は、再計算前の `inputs.json` を参照する。モデルの再生成は同じ文章を保証しない。実装や指示を変更して再実験する場合は、今回のフォルダーを保存し、別の日付・版の出力先を用意する。
